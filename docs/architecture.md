# Architecture

## Overview

The app is a single Flutter codebase in four layers. Each layer depends only on the ones below it.

| Layer | Folder | Holds | Depends on |
|---|---|---|---|
| Features | `lib/features/` | One folder per screen group: widgets and their controllers | Providers, domain |
| Providers | `lib/providers.dart` | Riverpod providers that wire everything together | Data, services, domain |
| Data and services | `lib/data/`, `lib/services/` | Firebase, the wger API, local storage, sensors, notifications | Domain |
| Domain | `lib/domain/` | Models and rules in pure Dart | Nothing |

The domain layer has no Flutter or Firebase imports. Streaks, weekly summaries and step counting are plain functions and classes, which is why they can be unit tested without a phone.

## State management

Riverpod, without code generation.

- **Repositories** are exposed through `Provider`s. `providers.dart` picks the Firebase or in-memory implementation once, at start-up.
- **Live data** (profile, workouts, habits, completions, step days) comes from `StreamProvider`s over Firestore snapshot streams. Screens rebuild when the data changes, including changes made offline.
- **Derived values** (streaks, weekly summary, today's totals) are `Provider`s that combine those streams with domain functions.
- **Screen state** that outlives a rebuild (the workout draft, the catalogue search, the step service) lives in `Notifier`s.

Screens read `AsyncValue` and render four states: loading, error with Retry, empty, and data.

## Navigation

go_router with a `StatefulShellRoute` for the four tabs. Paths:

| Path | Screen |
|---|---|
| `/splash` | Spinner shown while the sign-in state loads |
| `/auth` | S01 Account access |
| `/home` | S02 Home (tab) |
| `/workouts` | S03 Workout history (tab) |
| `/workouts/log` | S04 Workout log. Query: `mode=live`, `mode=past`, or `id=<workoutId>` to edit |
| `/exercises` | S05 Exercise catalogue |
| `/exercises/detail` | S06 Exercise detail (exercise passed as `extra`) |
| `/habits` | S07 Habits (tab) |
| `/habits/edit` | S08 Habit editor. Query: `id=<habitId>` to edit |
| `/steps` | S09 Steps and daily goal |
| `/progress` | S10 Progress (tab) |
| `/summary` | S11 Weekly summary |
| `/settings` | S12 Settings and profile |

A redirect sends signed-out users to `/auth` and signed-in users away from it. Picking an exercise uses `push` and `pop` with a result, so S06 returns the chosen exercise to S04.

## Data model (Cloud Firestore)

Everything a user owns sits under their own document.

```
users/{uid}                          profile and preferences
users/{uid}/workouts/{workoutId}     one document per workout, exercises and sets embedded
users/{uid}/habits/{habitId}         habit definition
users/{uid}/completions/{habitId_date}   one document per ticked habit per day
users/{uid}/steps/{yyyy-MM-dd}       one document per tracked day
```

| Document | Fields |
|---|---|
| Profile | `displayName`, `weeklyWorkoutTarget`, `stepGoal`, `stepTrackingEnabled`, `dailyReminderEnabled`, `dailyReminderMinutes` |
| Workout | `title`, `type` (`strength` or `timed`), `date` (yyyy-MM-dd), `startedAt`, `durationSeconds`, `exercises[]` (`exerciseId`, `name`, `category`, `sets[]` of `reps`, `weightKg`, `done`) |
| Habit | `name`, `weekdays[]` (1 = Monday), `reminderEnabled`, `reminderMinutes`, `startDate`, `archivedDate` (null while active) |
| Completion | `habitId`, `date` |
| Step day | `date`, `steps`, `goal`, `source` (`sensor` or `accelerometer`), `trackedFrom` |

Times (`startedAt`, `trackedFrom`) are stored as ISO 8601 text in the phone's local time.

Design choices:
- **Dates as `yyyy-MM-dd` strings.** A day is a calendar day in the phone's timezone. String keys sort correctly and avoid timezone conversion bugs.
- **Deterministic IDs.** Completions and step days use IDs built from their content, and a workout's ID is created with its draft. Writing the same thing twice overwrites one document.
- **Goal stored on each step day.** History keeps the goal that applied on that day.

### Security rules

`firestore.rules` allows a signed-in user to read and write only `users/{their uid}` and its subcollections. Everything else is denied.

## Offline behaviour

Firestore's built-in cache is the only local database.

- Reads are served from the cache when offline.
- Writes are queued and sent when the connection returns.
- A workout with a queued write reports `hasPendingWrites`, which the app shows as "Pending sync".
- Repository write methods return at once and do not wait for the server, because waiting would freeze the screen while offline.

Two small things live in SharedPreferences because they must survive before anything is saved to Firestore: the workout draft and the step tracker's last sensor reading.

## wger REST API

`WgerApi` calls `https://wger.de/api/v2/` with no API key.

| Need | Request |
|---|---|
| Browse | `GET exerciseinfo/?limit=20&offset=N&language__code=en` |
| Search by name | add `name__search=<text>` |
| Filter | add `category=<id>` and `equipment=<id>` |
| Filter lists | `GET exercisecategory/` and `GET equipment/` |

- The English translation is used for name and description. Exercises without one are skipped.
- Descriptions arrive as HTML and are reduced to plain text before display.
- Each successful page is cached in SharedPreferences under its query, and served from there when the network fails.
- Licence and author are shown on Exercise detail, as the wger content is CC-BY-SA.

## Step counting

```
sensor (pedometer or accelerometer) -> StepPlatform -> StepController -> StepTracker -> Firestore steps/{date}
```

- **Android step-counter sensor** reports steps since the phone booted. `StepTracker` keeps the last reading and adds the difference to today's total.
- **Phone restart:** the sensor restarts from zero, so a reading lower than the last one is treated as a fresh count.
- **New day:** the first reading of a day becomes that day's baseline. Steps taken before the app was first opened that day are not counted, and the screen shows the time recording started.
- **Fallback:** when no step-counter sensor exists, `StepDetector` counts peaks in accelerometer data while the app is open. The total is labelled as counted by the app.
- **No background service in V1.** This keeps the app free of foreground-service permissions.
- **Writes are batched.** Changes are saved 15 seconds after the first unsaved step, and when the app goes to the background.
- **iOS** uses the same plugin, which reads Core Motion. The system shows its own Motion & Fitness dialog the first time steps are read.

### Permission states

`StepController` exposes one status, and screens switch on it.

| Status | Meaning | What the user sees |
|---|---|---|
| `starting` | Checking permission after start-up | A placeholder card |
| `off` | Tracking not turned on | "Step tracking is off" and Enable |
| `denied` | Permission refused | "Step tracking is off", Enable, Continue without tracking |
| `permanentlyDenied` | Refused with "don't ask again" | Open settings |
| `unavailable` | No usable sensor | "Step counting is unavailable on this device" |
| `tracking` | Counting | Count, goal, progress bar |

## Notifications

`NotificationService` wraps `flutter_local_notifications`. All notifications are local, so no server is needed.

| Notification | When |
|---|---|
| Daily reminder | Every day at the time set in Settings |
| Habit reminder | At the habit's time on its scheduled weekdays |
| Step goal reached | Once per day, when the count passes the goal while tracking |

Scheduling uses inexact alarms, which need no special Android permission. Notification permission is requested only when the user turns a reminder on.

Reminders are cancelled at sign-out and scheduled again from the saved profile and habits the next time that account's records load (`features/shell.dart`).

## Demo mode

When `lib/firebase_options.dart` still holds placeholders, or the app is built with `--dart-define=DEMO=true`, the in-memory repositories are used and a banner says so. Nothing is sent to Firebase and data is lost when the app closes. This lets the app run before Firebase is set up and is what the widget tests use.
